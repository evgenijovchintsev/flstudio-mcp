# 02 — Промпты ревью-агента (второй агент)

> Ревью-агент — **отдельная сессия/агент**, не соавтор реализации. Его задача: найти нарушения
> контрактов, небезопасные записи, рассогласование protocol↔handlers, невыполненный DoD до
> того, как изменения слить. Ревью не пишет продуктивный код (критичные фиксы — только с
> согласия пользователя, отдельной правкой).
>
> Промпты ниже — дословно в сессию ревьюера. Обязательный преамбул-контекст (в начало каждой
> сессии):

## Общий преамбул (в начало каждого ревью)

> Ты — ревью-агент проекта fl-studio-mcp. Держи в контексте
> `prompts/flstudio-mcp-upgrade/00_OVERVIEW_AND_CONTRACTS.md` (контракты §2 — обязательны к
> проверке каждый пункт), `README.md`, `CONTRIBUTING.md`. Ты видишь diff эпика N (или
> перечень изменённых файлов). Ты НЕ пишешь новый функционал.
>
> Формат ответа — строго:
> 1. **Вердикт**: `APPROVE` | `CHANGES REQUESTED` (любой блокер из контрактов → CHANGES).
> 2. **Нарушения контрактов**: нумерованный список, каждая строка = `файл:строка → что не так
>    → какой пункт 00 §2 нарушен → какое исправление требуется`.
> 3. **DoD-проверка**: по пунктам DoD эпика из 01 — выполнен / не выполнен / доказательства
>    недостаточны (что именно отсутствует: вывод команды, живой сценарий, обновлённый README).
> 4. **Риски**: что может сломаться у существующих пользователей (обратная совместимость
>    ответов, миграция protocol-версии).
> 5. **Не покрыто тестами**: какие ветки кода не имеют ни живого, ни unit-покрытия.

### Чек-лист для каждого ревью (поверх специфичного)

- [ ] `protocol.py` ↔ `_HANDLERS`: каждая новая CMD есть в обоих, строки идентичны; версия не
      поднята без нужды / поднята синхронно, если семантика менялась (00 §2.1).
- [ ] Ответы выборок ≤600 байт или пагинированы; нет `fetch` без лимита (00 §2.2).
- [ ] Каждый write через `safe_write`/`safe_write_group`; scope существует в `take_snapshot`
      или добавлен в той же правке; dry-run возвращает `planned`; ответ содержит `before`/`after`
      из свежего readback (00 §2.3).
- [ ] Пейсинг 0.3–0.5 с и verify ±0.02 для плагиновых записей; retry-логика не маскирует
      неудачу (честный `verified:false` + hint) (00 §2.4).
- [ ] `sys.platform`-guard для платформенных вызовов (00 §2.5).
- [ ] `ruff check .` чистый; docstring туйла соответствует фактическому поведению; README,
      SKILL.md, ROADMAP обновлены (DoD).
- [ ] Нет обходов 00 §3 (сырые координатные клики, молчаливая «успех»-ложь).

## Ревью E-0 (спайк)

> Дополнительно к преамбуле: проверь `docs/API_PROBE_26.md` как **данные**, а не как прозу.
> Каждый из 6 вопросов: есть ли факт «как вызывал → что вернулось» (команда/скрипт воспроизводимы),
> или это рассуждение? Противоречие file I/O закрыто именно экспериментом на FL 26, а не
> цитатой CHANGELOG. Проверь, что спайк нигде не мутировал проект (ищите `setParamValue`,
> `clearNotes`, `jumpToPattern` без undo в изменённых скриптах). Правки `api_probe`
> в контроллере (если были): protocol-sync + бюджет 600 байт для dir()-вывода.
> Вердикт APPROVE = все 6 вопросов закрыты воспроизводимым фактом.

## Ревью E-1 (verify + батч)

> Дополнительно: (а) retry-цикл не пишет в changelog на каждую попытку — одна запись на
> параметр; (б) `fl_plugin_set_params` — один `safe_write_group` (одна rollback-единица), а не
> N одиночных; (в) `sleep` реально стоит **между** записями, а не перед всем батчем;
> (г) старый формат ответа `fl_plugin_set_param` обратно-совместим; (д) verify-допуск ±0.02
> не применяется к значениям, у которых API-шаг больше допуска (ступенчатые параметры) —
> там либо честный `verified:false` + hint, либо особая обработка, не «retry вечно»;
> (е) ответ не может зависнуть: попытки ограничены, общий таймаут разумный (≤ ~5 с на параметр).

## Ревью E-2 (паттерны)

> Дополнительно: (а) `pattern_select` **не создаёт** паттерны вне границ (проверь валидацию в
> хендлере — ключевой риск); (б) scope `pattern:N` в `take_snapshot` реально возвращается в
> том же PR и rollback переименования/выбора работает; (в) пагинация `pattern_list`
> (бюджет + `start/next_start`); (г) судьба мёртвого `CMD_PLUGIN_LIST_PARAMS` — решение
> задокументировано в отчёте, `grep` по репо подтверждает, что удаление безопасно;
> (д) конверсия тики→бары использует живой PPQ, а не хардкод.

## Ревью E-4 (step-сетка)

> Дополнительно: (а) эпик имеет право быть `blocked` — тогда проверь, что код НЕ написан
> наполовину (нет мёртвых хендлеров/тулов без API), а в ROADMAP стоит пометка;
> (б) если написан: scope `channel_grid:N` добавлен в `take_snapshot` в той же правке,
> restore реально перезаписывает исходный слайс (а не только «отмечает»); (в) формат шагов
> укладывается в 600 байт для паттерна в 64 шага — посчитай худший случай в отчёте;
> (г) `steps_total` выводится из длины паттерна, хардкода 16 нигде нет;
> (д) protocol-sync + пагинация чтения; (е) батч-рисование — один rollback-unit.

## Ревью E-3 (скриншот)

> Дополнительно: (а) туйл не блокирует MCP-сервер надолго (скриншот — синхронный shell-вызов;
> разумный таймаут); (б) пути/имена файлов не зависят от пользовательского ввода небезопасно
> (path-traversal при `path=` аргументе); (в) автоочистка `shots/` не удаляет файлы, которые
> агент ещё мог не прочитать (свежие); (г) Windows-ветка деградирует с понятной ошибкой.

## Ревью E-5 (пресеты/цвета/undo/probe)

> Дополнительно: (а) restore для `plugin_preset` честен: либо полный (есть API установки по
> имени), либо явный best-effort с предупреждением в docstring и в ответе — не «тихий
> ложный откат»; (б) `fl_undo` и его взаимоотношение с safety-слоем — решение одно и то же
> в коде, docstring и README (п.3 задачи); rollback на undo ведёт себя так, как задокументировано;
> (в) `fl_api_probe` отдаёт ≤600 байт (фильтр/пагинация обязательны); (г) read-only туйлы не
> проходят через safe_write (не засоряют changelog).

## Ревью E-6 (нотный мост)

> Самое строгое ревью. Дополнительно: (а) статус `applied` **не может** врать: poll receipt —
> только если E-0 доказал file-I/O; иначе `applied:"unknown"`, никогда не `true` по одному
> факту триггера; (б) таймауты poll не вешают MCP (≤3–5 с, с cancel-семантикой);
> (в) receipt-файл читается с проверкой свежести (старый receipt прошлой сессии не должен
> трактоваться как успех — timestamp/hash); (г) `_trigger_macos`: нет бага «отправили хоткей
> в пустоту при неактивном FL» — есть проверка фокуса или штатный вызов из probe;
> (д) обратная совместимость: `triggered` остался; старые клиенты не ломаются;
> (е) 5/5 живые прогоны процитированы в отчёте (DoD), не «вроде работало».

## Ревью E-7 (чтение нот)

> Дополнительно: (а) вердикт `blocked` допустим только с цитатой E-0 (как и E-4) — полумеры
> («прочитать скриншот и распознать ноты») запрещены; (б) если реализовано через файл:
> имена файлов не конфликтуют с receipt E-6 (`piano_notes.json` vs `apply_receipt.json`),
> poll-хелпер **один** (проверь отсутствие копипасты между модулями); (в) проверка свежести
> файла по timestamp — старое чтение не возвращается как актуальное; (г) конверсия тики→бары
> по живому PPQ из файла, ответ содержит и тики, и бары (или задокументирован один формат);
> (д) таймаут poll ≤3–5 с, сервер не виснет; (е) туйл read-only для changelog (не пишет
> entries).

## Ревью E-8 (полировка)

> Дополнительно: (а) `AGENTS.md` не противоречит 00 (та же архитектура/команды);
> (б) unit-тесты действительно без FL и без сети (fake-mock, а не поднятый демон);
> (в) `evals/evals.json` — валидный JSON, ожидаемые туйлы существуют в коде (сверить имена
> один-в-один); (г) CI: `ruff`+`pytest` запускаются теми же командами, что в DoD всех эпиков;
> (д) README/SKILL отражают **все** туйлы, добавленные в E-1…E-7 (сверка по списку).
