## Epic E-1 — Надёжность записи параметров: verify + батч

> Проблема (00 §4): `fl_plugin_set_param` молча возвращает `after`, даже если запись была
> съедена pickup-режимом. Плюс сессия выявила: одиночные записи требуют пауз 0.3–0.5 с.
>
> Шаги:
> 1. В `tools/plugin.py` расширить write-путь `fl_plugin_set_param`: после `safe_write`
>    сверить `after.v` с запрошенным нормализованным значением (допуск ±0.02); при расхождении
>    — **re-read + retry** (до 3 попыток, пауза 0.4 с; это живой пейсинг, не `_verify_retry`
>    с 0.06 с — он для toggle). В ответ добавить явные поля `verified: bool`,
>    `attempts: int`, `hint` («плагин не принял значение — окно плагина открыто? pickup mode?»).
>    Retry — внутри туйла, но changelog-запись одна (не плодить записи).
> 2. Новый туйл `fl_plugin_set_params(track, slot, writes)` — батч: список
>    `[{param, value}, …]` через **один** `safety.safe_write_group` (один rollback-unit),
>    с `time.sleep(0.4)` между записями. Тот же verify-механизм на каждую, ответ — массив
>    per-param `{param, ok, verified, before, after}`.
> 3. Docstring обоих тулов: рецептура из 00 §3 (закрыть окно плагина, ступенчатые параметры
>    API не пишутся, нормализованные 0..1).
> 4. Существующий `fl_plugin_set_param` обязан остаться обратно-совместимым (новые поля —
>    добавка, не замена `before`/`after`).
>
> Протестировать на живом FL: `fl_plugin_set_params` на Fruity Parametric EQ 2 (несколько
> band-параметров) → `fl_plugin_get_params` сверяет фактические значения →
> `fl_rollback_last_change` возвращает исходные → повторное чтение подтверждает откат.

**DoD:** оба туйла работают на живом FL; `verified:false` честно возвращается, если значение
не принято (проверить симуляцией: открыть окно плагина и записать — получить false+hint);
rollback батча откатывает все параметры разом; `ruff check .` чистый; README-раздел плагинов
и SKILL.md обновлены (рецепт + батч).

**Проверка:** `ruff check .` + живой сценарий выше, процитированный в отчёте + unit-тест
mock-моста, если он уже влит из E-8 (иначе живой).

> (например, `channels.getStepData`/`setStepData`); если API нет — эпик закрывается статусом

>
> Если API есть:
>
> 1. Хендлеры в контроллере: `channel_get_grid` (чтение сетки одного канала, шаги 0..N —
>    пагинация/слайсы по `start`/`count`, бюджет 600 байт), `channel_set_grid_bit`
>    (значение шага 0..127 — velocity; 0 = выкл), `channel_clear_grid` (диапазон шагов).
>    Добавить `CMD_*` в protocol.py синхронно (00 §2.1). Формат шагов: массив чисел или
>    run-length для экономии байт — решение зафиксировать в отчёте, бюджет соблюсти.

# ЧАСТЬ D. Нотный мост

## Epic E-6 — Note-bridge: подтверждение применения + macOS-триггер

> Главная боль прошлой сессии: `triggered: true` ≠ ноты применились; arm «MCP Apply» — вручную;
> Cmd+Opt+Y не срабатывал. Опирается на факты E-0 п.2 и п.3.
>
> 1. **Если E-0 п.2 подтвердил write в песочнице**: генерируемый `MCP_Apply.pyscript`
>    (pyscript_gen.py) в конце пишет receipt `~/.flstudio-mcp/apply_receipt.json`
>    (timestamp, count, mode, hash нот). После триггера `FLBridge.apply_notes` опрашивает
>    receipt (poll до 3 с, 0.25 с интервал) и возвращает `{"triggered": true, "applied":
>    true, "receipt": {...}}`. Нет receipt за таймаут → `applied: false` + hint («FL не
>    выполнил скрипт — запусти MCP Apply вручную»). Поле `applied` — **новое**, `triggered`
>    остаётся для обратной совместимости.
> 2. **Если write запрещён**: честный вариант — receipt невозможен; тогда хотя бы
>    детект «скрипт выполнился» через другой сигнал (например, генерируемый скрипт трогает
>    score-секцию и controller-хендлер `pattern_get_length`/спец. probe-команду видит
>    изменение — только если это надёжно; если нет — ограничиться честным `applied: "unknown"`
>    + инструкцией). Ничего не выдумывать: только доказанный механизм.
> 3. **macOS-триггер** по фактам E-0 п.3: если штатный вызов есть (п.3 probe) — использовать
>    его (идеально, без хоткеев); иначе — починить `_trigger_macos` (фокус → пауза →
>    конкретный путь, проверенный спайком) и добавить в ответ триггера поле
>    `focus_ok`/`method` для диагностики. Прогнать 5 раз подряд без ручного вмешательства.
> 4. `fl_write_piano_roll_notes` (tools/pianoroll.py) и RPC `apply_notes` — прокинуть
>    `applied`/`receipt` наружу, обновить docstring (что означает каждый статус).
> 5. SKILL.md: раздел «нотный мост» — три статуса (applied/needs-manual/unknown) и рецепт
>    ручного arm.
>
> Живой тест: заменить ноты в тест-паттерне → получить `applied: true` → проверить receipt →
> `fl_rollback` не нужен (ноты — замена в том же паттерне; вернуть прежние ноты копией из
> changelog или переписать исходными, сохранив их ДО теста).

**DoD:** статус `applied` реальный (или честный `unknown` с доказанной невозможностью),

## Epic E-7 — Чтение нот из Piano roll: `fl_piano_get_notes`

> Сегодня сервер умеет только **писать** ноты (односторонний мост): агент не может сверить,
> что реально лежит в паттерне, кроме скриншота. Это закрывает контур «прочитал → записал →
> сверил» и делает возможным честный rollback нот.
>
> Опирается на факты E-0 п.2 (что разрешено в песочнице) и на устройство моста:
> генерация `.pyscript` с вшитыми данными работает в обоих направлениях (файл пишет демон).
>
> 1. **Если file I/O в песочнице разрешён** (E-0 п.2): генерировать `MCP_Read.pyscript`,
>    который сериализует текущий score в `~/.flstudio-mcp/piano_notes.json`
>    (pitch, time_ticks, length_ticks, velocity; плюс `ppq`), триггерить тем же механизмом,
>    ждать файл (poll ≤3 с, свежесть по timestamp), отдавать массив нот + конвертировать
>    тики → бары на сервере. Туйл `fl_piano_get_notes(channel=None, start_bar, end_bar)`.
> 2. **Если запрещён** — рассмотреть альтернативный путь через контроллер, если E-0 нашёл
>    читаемый API нот из `dir(...)` (маловероятно, но probe обязателен); если и его нет —
>    эпик `blocked` с цитатой E-0 (DoD допускает), без чтения скриншотов «на глаз».
> 3. Read-only туйл (запись в файл — служебная, вне FL). Но поскольку файл-приёмник может
>    конфликтовать с receipt E-6 — разные имена файлов, общий poll-хелпер в connection/
>    отдельном модуле, никакого дублирования логики.
> 4. Использование: `fl_write_piano_roll_notes(mode="append")` → `fl_piano_get_notes` сверяет
>    фактическое; «что сейчас в паттерне» перед решением писать/не писать.
>
> Живой тест: прочитать ноты тест-канала → сверить с Channel Rack/пiano roll глазами →
> записать одну тест-ноту append → повторное чтение её содержит → удалить тест-ноту (replace
> исходными, сохранёнными до теста) → чтение совпадает с исходным.

**DoD:** либо туйл с живым сценарием (прочитанное = реально лежащее), либо честный `blocked`
с доказательством из E-0. `ruff check .`; README/SKILL; нет дублирования poll-логики с E-6.

**Проверка:** `ruff check .`; `python scripts/test_bridge.py`; живой сценарий.

## Порядок реализации

```
E-0 (spike, всё чинит) → E-1 (надёжность) → E-2 (паттерны) → E-4 (step-сетка)
  → E-3 (скриншот) → E-5 (пресеты/цвета/undo/probe) → E-6 (нотный мост)
  → E-7 (чтение нот) → E-8 (полировка)
```

E-3 и E-5 независимы после E-0; E-4 — только при подтверждённом API (иначе `blocked`);
E-6 зависит от вердикта E-0 п.2/п.3; E-7 следует после E-6 (общий poll-хелпер);
E-8 — последний. После каждого эпика — ревью (02) и функциональный тест (03) с тем же номером.
